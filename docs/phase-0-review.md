# AIS COMPANY — PHASE 0
# مراجعة المواصفات وتثبيت الخطة

## 1. الملخص التنفيذي

المواصفات غنية ومناسبة لبناء نظام مالي حقيقي، لكنها ليست جاهزة للتنفيذ المباشر قبل تثبيت بعض القواعد المالية والتقنية. نقطة 1 تحدد نطاق النظام وقواعد العمل، ونقطة 3 تلزمنا بمراجعة هذه القواعد وتوثيقها قبل كتابة الكود.

القرار: لا يبدأ التنفيذ الفعلي قبل اعتماد النسخة المصححة من المواصفات وبوابات القبول في هذا المستند.

## 2. نطاق AIS النهائي

النظام هو نظام توثيق وإدارة حوالات وعلاقات مالية لشركة AIS. لا ينفذ تحويلات مصرفية خارجية ولا يضيف مخزوناً أو مبيعات أو ضرائب أو رواتب أو تكاملاً مصرفياً.

الوحدات الأساسية:

- تسجيل الدخول والصلاحيات.
- الأشخاص والمكاتب والشركات.
- حساب واحد لكل جهة، مع أرصدة مستقلة لكل عملة.
- الحوالات المرسلة والمستلمة.
- التسويات.
- الأرصدة الافتتاحية وكشوف الحساب.
- التقارير والطباعة والتصدير.
- العمل Offline والمزامنة التلقائية.
- سجل التدقيق والنسخ الاحتياطي.

## 3. المشاكل الحرجة وتصحيحها

### C-01 — غموض أثر الحوالة المستلمة

التصحيح المعتمد مبدئياً: الحوالة المرسلة من AIS عبر الجهة تزيد ما نطلبه من الجهة. الحوالة المستلمة من الجهة إلى AIS تزيد ما تطلبه الجهة من AIS.

### C-02 — Last Write Wins في البيانات المالية

سيطبق آخر تعديل ناجح على النسخة الحالية، لكن لا تُمحى النسخة السابقة. كل تعديل يحفظ الإصدار السابق والجديد والمستخدم والجهاز والوقت في سجل التدقيق. لا يُسمح بتعديل صامت.

### C-03 — تسلسل الأرقام أثناء Offline

UUID هو المعرف التقني. الأرقام P/O/C/S هي معرفات تجارية. عند الاتصال يحجز الخادم نطاق أرقام لكل جهاز. لا يسمح النظام بإنشاء رقم تجاري متسلسل جديد بعد نفاد النطاق حتى يتم الحجز من الخادم، إلا إذا تم اعتماد سياسة أرقام مؤقتة.

### C-04 — المزامنة الخلفية على iOS

لا يمكن ضمان تشغيل خلفية مستمر في Safari/PWA. يضمن النظام المزامنة عند فتح التطبيق، وعند عودة الاتصال، وأثناء بقاء التطبيق نشطاً، ويستخدم Background Sync عندما يدعمه النظام.

### C-05 — الحذف المالي

الحذف من البيانات النشطة يكون حذفاً منطقياً مع سبب حذف. يعكس الأثر المالي ويحتفظ بسجل التدقيق. لا يستخدم Hard Delete للسجلات التي تؤثر في التاريخ المالي.

### C-06 — الحسابات الثابتة

الحسابان AIS وUser يزرعان في الخادم بكلمات مرور مجزأة من متغيرات بيئية أو خطوة إعداد آمنة. لا تظهر كلمات المرور في الواجهة أو المصدر أو السجلات.

## 4. النموذج المالي الرسمي

كل عملية مالية تستخدم عملة واحدة فقط، وكل الحسابات مستقلة حسب العملة. لا توجد تحويلات أو أسعار صرف أو جمع بين العملات.

### اتجاهات الحساب

- `نطلبه`: مبلغ مستحق لـ AIS على الجهة.
- `يطلبنا`: مبلغ مستحق للجهة على AIS.

### أثر الحوالات

| العملية | الأثر |
|---|---|
| حوالة مرسلة | تزيد `نطلبه` بقيمة `total` |
| حوالة مستلمة | تزيد `يطلبنا` بقيمة `total` |

`total = amount + commission`، وتُحفظ العمولة منفصلة للتقارير.

### أثر التسويات

- `هم دفعوا لنا`: تقلل `نطلبه` أولاً، وإذا تجاوزت الرصيد تنتقل الزيادة إلى `يطلبنا`.
- `نحن دفعنا لهم`: تقلل `يطلبنا` أولاً، وإذا تجاوزت الرصيد تنتقل الزيادة إلى `نطلبه`.

### مثال حتمي

الرصيد الافتتاحي: نطلبه USD 5,000.

حوالة مرسلة: amount USD 10,000، commission USD 50، total USD 10,050.

هم دفعوا لنا USD 3,000.

النتيجة: نطلبه USD 12,050.

إذا كان الرصيد نطلبه USD 3,000 ودفعوا لنا USD 10,000، فالنتيجة: يطلبنا USD 7,000.

### قواعد التحقق

- amount أكبر من صفر.
- commission لا تقل عن صفر.
- total محسوب في الخادم وليس من الواجهة فقط.
- settlement amount أكبر من صفر.
- العملة من القائمة الخماسية فقط.
- لا تحفظ عملية جزئية أو غير صالحة.

## 5. العمارة المقترحة

- **Frontend:** React + TypeScript + Vite، SPA/PWA، RTL، IndexedDB للتخزين المحلي.
- **Local data:** IndexedDB عبر طبقة repository، مع outbox للمزامنة. لا يعتمد النظام على localStorage كقاعدة مالية.
- **Backend:** Node.js + TypeScript، طبقات API وdomain/services وrepositories.
- **Database:** PostgreSQL عبر Prisma، Decimal/Numeric للمبالغ، معاملات قاعدة بيانات ذرية.
- **Shared contracts:** أنواع TypeScript وZod schemas مشتركة بين العميل والخادم.
- **Auth:** جلسة آمنة أو access/refresh tokens في cookies آمنة، مع authorization server-side.
- **PWA:** manifest، service worker، cache strategy، وإدارة إصدار واضحة.

## 6. نموذج البيانات المفاهيمي

- `User`: مستخدم ثابت، role، passwordHash، active.
- `Party`: جهة موحدة بنوع PERSON/OFFICE/COMPANY وبيانات مشتركة وحالة active/archived.
- `PersonProfile`, `OfficeProfile`, `CompanyProfile`: بيانات النوع فقط.
- `Currency`: قائمة ثابتة USD/IQD/IRR_TOMAN/EUR/SAR.
- `OpeningBalance`: جهة + عملة + اتجاه + Decimal، بدون تاريخ عملية.
- `Transfer`: UUID، businessNumber، party، direction، date، sender، recipient/beneficiary، location، currency، amount، commission، total، notes، version، timestamps، deletedAt.
- `Settlement`: UUID، businessNumber، party، direction، currency، amount، notes، version، timestamps، deletedAt.
- `LedgerEffect`: أثر مشتق/مسجل لكل عملية، جهة + عملة + اتجاه + Decimal، لضمان قابلية التتبع وإعادة الحساب.
- `AuditLog`: action، entity، oldValues، newValues، reason، user، device، timestamp.
- `SyncMutation`: mutationId، entityId، operation، payload، status، attempts، lastError، timestamps.
- `NumberBlock`: نوع الرقم، الجهاز، بداية النطاق، نهايته، المستهلك، والحالة.
- `Device`: معرف الجهاز، آخر اتصال، آخر sync cursor.
- `BackupMetadata`: وقت النسخة، الحالة، الحجم، checksum، retention class.

المعرف الأساسي لكل كيان UUID. الرقم التجاري فريد بقيود قاعدة البيانات ولا يستخدم كمفتاح أجنبي.

## 7. API المفاهيمي

- `/auth`: login، logout، session.
- `/parties`: list، search، create، update، archive.
- `/transfers`: list، filters، create، update، soft-delete، details.
- `/settlements`: list، create، update، soft-delete.
- `/accounts`: balances حسب الجهة والعملة.
- `/statements`: كشف حساب قابل للتصفية والطباعة.
- `/reports`: account، transfer، settlement، balance، commission.
- `/sync`: push mutations، pull changes، acknowledge، cursor.
- `/audit`: للمدير فقط.
- `/system`: health، sync status، backup status.

لا يتصل المتصفح بـ PostgreSQL مباشرة.

## 8. خطة Offline والمزامنة

1. يكتب المستخدم إلى IndexedDB داخل transaction محلية.
2. تحفظ العملية في outbox بمعرف mutationId ثابت.
3. تظهر العملية فوراً محلياً مع حالة Pending.
4. عند الاتصال يرسل العميل mutationId والنسخة المتوقعة.
5. ينفذ الخادم العملية Idempotently داخل transaction.
6. يعيد الخادم acknowledgment وversion وbusiness number.
7. يسحب العميل التغييرات منذ sync cursor.
8. يعيد المحاولة بتدرج زمني، ولا ينشئ طلباً جديداً لنفس mutationId.
9. عند تعارض التعديل يطبق آخر نسخة ناجحة مع حفظ التعارض في AuditLog.
10. لا يعتبر السجل Synced قبل acknowledgment صريح من الخادم.

## 9. الصلاحيات

### AIS

صلاحية كاملة: إنشاء وتعديل وحذف منطقي وإدارة الجهات والتسويات والإعدادات والتقارير والتدقيق.

### User

قراءة فقط للحوالات والجهات وكشوف الحساب والطباعة والتصدير المسموح. لا تظهر له الإعدادات أو الإنشاء أو التعديل أو الحذف أو التسويات أو سجل التدقيق.

التحقق من الصلاحية يتم في API حتى لو تم تعديل الواجهة يدوياً.

## 10. التعارضات المتبقية التي تحتاج اعتماداً

1. هل المقصود بالحوالة المستلمة دائماً أن الجهة أرسلت المال إلى AIS؟ هذا هو الافتراض المستخدم في النموذج أعلاه.
2. هل نعتمد حجز نطاقات الأرقام عند الاتصال، أم نسمح برقم مؤقت للعمل Offline عند نفاد النطاق؟ التوصية: حجز النطاقات فقط.
3. هل يسمح بإدخال رصيد افتتاحي موجب في الاتجاهين للعملة نفسها؟ التوصية: حفظ الإدخالات الخام، لكن عرض صافي واضح مع تحذير عند وجود الاتجاهين.
4. هل التعديل بعد وجود تسويات يسمح بتغيير العملة أو الجهة؟ التوصية: لا؛ ينشأ تصحيح/عكس ثم عملية جديدة للحفاظ على سلامة التاريخ.
